2026-09-21 리서치와 가독성 검토를 반영한 교체 시안이다. 9월 20일 승인된 판단 중심 흐름을 유지한다. 목표 동작을 설명하는 문서이며 앱 구현 완료를 뜻하지 않는다.

### 실제 자료와 예시의 구분

- **실제:** 세 작업 묶음의 영문 원문, 파일 목록과 겹침, 분석·관찰 시각, 관찰 범위 제한, 확인된 목표 부재.
- **설계 해석:** 사용자 언어로 바꾼 작업명과 기능 설명, 정책에 비추어 가능한 기대 효과. 이전 사용자 의도의 인용이 아니다.
- **예시:** 범위 확인 완료, 질문에 대한 답변, 남겨두기 결정, 유효한 방향, 완료 보고, 충돌하는 방향, 실행 후 부분 처리. 상태 예시 문구·출처 줄·상단 장면 표시로 구분한다.
- **미확인:** 시작 계기, 최신 동작, 최신 범위의 검증, 실제 성능·사용성 효과. 문구로 채우지 않는다.

## 3. 정보 구조와 화면별 결정

### 공통 구성

프로젝트 이름 → 조용한 방향 표시 → **현재 판단** → 필요한 근거 → 다른 작업 순서다.

0depth는 구체적인 작업명, 기록된 변경, 현재 진행 상태, 판단에 중요한 미확인 사항, 다음 행동이다. 진행 상태와 중요한 미확인은 접지 않는다. 1depth는 상세한 변경 설명, 기대 효과와 해석, 출처와 한계다. 원본 기록은 설명된 근거에서 명시적으로 연다. 깊이는 화면 수가 아니며, 1depth는 반드시 거쳐야 하는 단계가 아니다.

초기 진입에서 세 작업의 긴 설명을 모두 읽게 하지 않는다. 현재 작업의 상황과 다음 행동을 함께 본다. 다른 작업은 하단의 짧은 목록에서 바꾼다. 첫 작업 표시는 탐색의 초기값이며 추천 우선순위나 사용자 의도를 확정하지 않는다. 실제 행동은 현재 표시된 작업을 대상으로 선택한다.

| --------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------ |

| 완료 가능성·방향 변화 | 마쳤다고 볼까요? / 유지할까요? 보고와 미확인 사실                              | 방향 논의 → 유지·수정·마무리 결정                                                 | 완료 보고 또는 달라진 정보                             |

| 작업 맥락 부족        | 무엇을 하던 변경인지 함께 확인할까요? 작업 분류 미확정                         | 맥락 논의, 실행 범위 확정은 보류                                                  | 알려진 변경과 부족한 입력                              |

### 선택별 진행

- 이어가기: 내용·범위 논의 → 처리 내용과 범위 검토 → 사용자 확정 → 요청 준비.
- 커밋: 커밋 대상·남길 수정·검증 결과 검토 → 사용자 범위 확정 → 요청 준비.
- 되돌리기: 없어질 수정·남길 수정 검토. staged 해제와 수정 폐기를 구분 → 사용자 확정 → 요청 준비.
- 필요성 논의: 질문에 답한 뒤 원래 판단으로 복귀. 대화 자체를 실행 의도로 기록하지 않는다.
- 남겨두기: 대상과 결정을 보존. 나머지 미결정 변경이 있으면 그 판단을 보여주고, 모두 남겼다면 방향 흐름으로 이동.

처리 방법은 범위 확정 전에도 볼 수 있다. 정확한 범위 확인은 실행 전 조건이다. 기존의 별도 작업 선택·상세 설명·범위 확인·처리 방법 마법사 경로를 기본 동선에서 제거했다. 이전 시안에서 저장된 화면 위치는 현재 판단 또는 범위 검토로 연결한다.

주된 행동은 상태에 맞게 달라진다. 동작 미확인 시 확인 항목과 요청을 준비하고, 남은 수정이 확인된 예시에서는 수정 논의, 동작을 확인한 예시에서는 커밋 범위 검토를 앞세운다. 남겨두기는 가까이 두고, 나머지 처리 방법은 낮은 강조의 텍스트 버튼으로 유지한다. 선택지 수를 임의로 세 개로 제한하지 않는다.

### 답변 형식

질문에 대한 직접적인 답 → 짧은 이유 → 다음에 확인할 내용 순서다. 긴 수식어를 작업명에서 제거하고, 출처를 가까이 표시한 뒤 보고된 내용을 직접 서술한다. 근거와 원문은 답변 아래 선택적으로 펼친다. 예시 답변은 미리 작성한 샘플임을 답변 자체에도 표시한다. 실제 질문을 분석하는 기능은 이 시안에 없다.

### 가독성 설계

- 제목에는 구체적인 작업을 쓴다. “지금 판단할 내용” 같은 안내 문구를 반복하지 않는다.
- “기록된 변경”과 “아직 미확인”을 정의 목록으로 구분한다. 작업의 동작 여부는 0depth에 남긴다.
- “기록된 변경”은 가까운 “이전 분석” 출처 아래의 보고 내용이다. 관찰이나 검증 결과로 승격하지 않는다.
- 한 문장에 변경 내용, 추정, 한계를 모두 넣지 않는다. 짧은 설명은 문장으로 유지하고 비교할 내용만 구조화한다.
- 본문은 16px, 줄 간격 1.75, 작업명은 32px(좁은 화면 28px)이다. 한국어 단어 단위 줄바꿈과 긴 문자열 넘침을 함께 처리한다.
- 중요한 미확인을 흐린 보조 문구로 처리하지 않는다. 출처 시점·검토 도구·보존 안내만 낮은 강조로 둔다.
- 주요 버튼은 넓은 화면에서 내용에 맞는 폭, 좁은 화면에서는 한 줄 전체 폭을 사용한다.
- 장면 선택과 시안 조작은 제품 화면 밖 접힌 검토 도구로 이동한다. 새 검토 링크의 preview=03은 이전 시안의 초안과 별도 저장 공간을 쓴다.

### 실제 근거와 이상적 상태 예시

기본 장면은 기존 실제 저장 분석이다. 정상 동작, 완료, 성능 향상을 추가 사실로 만들지 않는다. “남은 수정이 확인됨”과 “동작 확인 후 커밋 검토” 장면만 별도로 제공하며 실제 결과가 아닌 상태 예시임을 작업 설명 옆에 표시한다.

새 동작 확인 경로는 확인할 항목 → 수정 없이 확인하는 요청문 → 결과 대기다. 시안은 확인 요청을 실제 전송하지 않는다. 실제 결과가 없으면 대기 상태로 남으며 버튼 클릭만으로 확인 완료로 바뀌지 않는다. 읽기·확인 요청과 수정·커밋·되돌리기 요청의 범위 확정 조건을 구분한다.

### 보존·불확실성·복귀

초기 로딩은 프로젝트 이름부터 보여주고 빈 결과와 구분한다. 갱신 중·실패에도 이전 설명과 초안을 유지한다. 상태 미확인을 변경 없음으로 바꾸지 않는다. 같은 상태의 남겨두기 결정을 반복해서 묻지 않는다. 관련 새 정보가 있으면 해당 작업만 재검토하며 이전 결정은 유지한다. Git 변경이 없어도 결과 검토가 남아 있으면 그 검토가 현재 판단이다.

정책 변경을 선택하면 승인 범위와 정책 반영을 다음 작업으로 기록한다. 정책을 논의하거나 목표를 저장한 사실만으로 충돌을 해결했다고 표시하지 않는다. 실제 정책 반영 확인 전에는 충돌하는 작업을 진행하지 않는다. 현재 방향을 마쳤다고 기록하면 새 목표를 강제하지 않고 종료할 수 있다.

## 4. 행동과 상태 보존 계약

### 행동 의미

- **이어하기:** 현재 작업에서 더 할 내용과 범위를 StateCarry 안에서 논의하고 완료 조건을 확인한 뒤 요청 준비. 바로 실행하지 않는다.
- **커밋:** 선택한 수정, 제외할 수정, 검증 결과를 검토한다. staged라는 이유로 전부 포함하지 않는다. 미검증과 실패를 구분한다.
- **되돌리기:** 없어질 내용과 남길 내용, 영향을 확인한다. staged 상태만 해제하는 요청과 수정 내용을 폐기하는 요청을 구분한다.
- **그대로 두기:** 범위와 관찰 상태에 연결된 사용자 결정을 기록한다. 일부만 남겼다면 나머지 변경을 이어서 다룬다. 남겨둔 변경과 새 작업이 겹치면 해당 부분을 설명한다.
- **조금 더 논의:** 필요성·기대 효과·범위를 비교한다. 답변을 보았다는 이유로 결정을 기록하지 않는다. 언제든 초안을 보존하고 나갈 수 있다.
- **분류 수정:** 사용자 설명과 범위 정정을 원래 분석과 구분해 기록한다. 정정만으로 실제 파일 범위가 확정됐다고 보지 않는다.
- **방향·정책 논의:** Codex 요청 준비 → 외부 논의 → 돌아온 결과 검토 → 명시적 확인. 정책 변경을 택했다고 충돌이 해결된 것은 아니다. 필요한 정책 수정·검토가 다음 작업에 포함돼야 한다.
- **실행 후 확인:** 요청과 현재 관찰을 비교한다. 성공 보고, 관찰 결과, 검증 결과, 사용자 수락은 별개의 사실이다. 일부만 처리했으면 나머지와 이전 보류 결정을 유지한다.

### 보존과 무효화

| 상황                          | 보존                                                                | 다시 확인할 것                                                    |
| ----------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 논의 닫기·다른 화면·앱 재시작 | 선택 작업/범위, 대화, 미전송 입력, 요청 초안, 근거 공개와 읽던 위치 | 외부 상태의 최신성                                                |
| 갱신 중                       | 마지막 유효 설명, 작성 중 내용, 현재 화면                           | 확인 완료 시 달라진 부분만 알림                                   |
| 근거 변경                     | 이전 답변을 당시 근거에 붙여 보존                                   | 현재 상태로 논의를 이어갈지 확인. 요청 범위는 재검토              |
| 관련 없는 변경                | 보류와 선택                                                         | 영향 관계가 없으면 재확인 요구 안 함                              |
| 묶음 이름/구성 변경           | 이전 작업 설명, 논의, 선택                                          | 대응 불명확하면 사용자에게 연결 확인. 제목 변경으로 삭제하지 않음 |
| 응답 대기 중 이탈             | 질문의 작업 ID와 근거, 입력                                         | 늦은 응답은 원래 논의에 붙임. 다른 화면으로 이동시키지 않음       |
| 요청 복사 후 변경             | 수정한 요청문, 준비 이력                                            | 최신 범위 재검토 전 실행용 복사 제한                              |
| 원본 기록 이탈/복귀           | 직전 화면·입력·스크롤·포커스                                        | 기록 열람 자체로 의사 결정 없음                                   |
| 저장 실패                     | 메모리의 입력·선택                                                  | 저장 실패 명시, 재시도와 내용 복사. 저장 성공으로 표시하지 않음   |
| 실행 일부 실패·부분 완료      | 요청, 보고, 이전 보류                                               | 범위별 관찰을 비교, 자동 완료 없음                                |

‘나중에 결정’은 ‘변경을 그대로 두기’와 다르다. 논의 이탈만으로 보류 범위를 자동 기록하지 않는다. 일반 중단 결정도 파일 되돌리기와 분리한다.

### 접근성·모바일

제목 계층, 명시적인 입력 레이블, 키보드 조작, 보이는 포커스, 색상에 의존하지 않는 미확인·예시 표시를 사용한다. 새 상태 알림은 읽기 흐름을 강제로 이동시키지 않는다. 논의 열기·닫기에는 제목/원래 버튼으로 포커스를 복귀시킨다. 동적 갱신이 입력 포커스나 커서 위치를 초기화하지 않아야 한다. 390px 시안과 실제 좁은 브라우저에서 줄바꿈·버튼·입력 폭을 점검한다.

## 5. 필요한 데이터와 현재 구현 대비

### 입력 → 출력 변경

| 입력                                       | 필요한 출력과 구분                        | 없을 때                                                |
| ------------------------------------------ | ----------------------------------------- | ------------------------------------------------------ |
| 변경과 연결된 사용자 요청·결정·관련 문서   | 시작 배경, 귀속 주체, 근거 참조           | 시작 계기 미확인. Codex 대화를 필수로 요구하지 않음    |
| 현재 diff·관련 코드·관찰 한계              | 현재 반영 내용의 문장별 근거              | 확인한 범위만 설명                                     |
| 목적·목표·정책과 변경의 관계               | 기대 효과와 이유, 측정된 효과와의 구분    | 가능한 효과는 해석, 성과는 미확인                      |
| staged/unstaged/미추적 내용과 수정 구간    | 포함/제외, 겹침·의존 관계, 범위 근거 버전 | 파일 목록만으로 커밋/되돌리기 범위 확정 금지           |
| 검증 대상·시각·결과·코드 상태              | 적용 가능한 검증 결과와 적용 한계         | 미검증과 실패 구분                                     |
| 사용자 목표 확인·정책 결정                 | 제안/확인된 방향, 충돌과 해결 상태        | 문서를 사용자 결정으로 승격하지 않음                   |
| 범위별 보류·선택과 당시 변경 상태          | 결정 이력과 영향 기반 재검토              | 프로젝트 전체 fingerprint 변경으로 모든 보류 해제 금지 |
| 요청 ID, 확인된 범위, 외부 보고, 후속 관찰 | 준비/복사/실행 미확인/부분 처리/결과 검토 | 복사를 성공한 작업으로 처리하지 않음                   |

저장된 설명에는 각 주장별로 `관찰 / 기록된 사용자 요청·결정 / 에이전트 보고 / StateCarry 해석·제안 / 미확인`을 구분할 수 있는 정보와 원본 참조가 필요하다. 분류 결과와 사용자 선택은 별도다. 그룹의 안정적 식별과 근거 버전도 분리한다.

필요한 인터페이스 변화는 분석 출력의 근거·배경·효과 구분, 범위 검토의 수정 구간/겹침, 범위별 사용자 결정과 초안, 요청과 실제 결과 연결이다. 이 설계 작업에서는 API·DB·타입을 추가하지 않는다. 다음 구현에서 기존 계약을 확장하며 오래된 분석은 ‘배경 미확인’, ‘범위 미확정’으로 읽는다. 기존 사용자 초안은 유지하고 분석의 추천을 기존 사용자 선택으로 변환하지 않는다.

### 현재 구현과의 차이

| 현재 구현 또는 이전 시안                 | 이번 설계                                              |
| ---------------------------------------- | ------------------------------------------------------ |
| 그룹 선택과 설명이 별도 단계             | 현재 판단 안에서 작업을 바꾸고 맥락과 행동을 함께 확인 |
| 설명 → 범위 → 처리 방법                  | 판단 → 선택한 행동에 필요한 논의·범위 검토             |
| 이어갈 내용 논의 / 조금 더 논의가 비슷함 | 이어가기 의도와 필요성 검토를 분리                     |
| 커밋·되돌리기·남겨두기가 접힘            | 판단 영역에서 직접 발견 가능한 선택                    |
| 긴 문단 답변                             | 답·이유·다음 확인을 구분하고 근거는 선택 공개          |
| 작업을 파일 목록과 제목으로 식별         | 안정적인 작업 식별자, 수정 구간 범위, 근거 버전 필요   |
| 전체 변경 상태로 보류 판단               | 작업 범위별 보존과 관련 변경만 재검토                  |

추가로 필요한 출력은 currentDecision(질문·대상 작업·핵심 맥락·중요한 미확인), availableChoices(행동 의미·다음 시나리오·실행 조건), answer(결론·이유·다음 확인·근거 참조)다. 이 이름은 설계 개념이며 현재 API에 구현된 필드가 아니다. 데이터가 없으면 단정적인 문구로 채우지 않는다.

## 6. 검토 기준

- 첫 화면에서 판단 대상과 선택을 함께 확인할 수 있는가?
- 근거를 읽지 않아도 현재 판단을 이해하고, 필요하면 같은 자리에서 더 살펴볼 수 있는가?
- 선택한 행동에 맞는 범위를 확인하며, 범위 미확정 상태에서 실행 요청을 만들지 않는가?
- 논의의 답·이유·다음 확인이 구별되는가?
- 보류·이탈·복귀·갱신 시 선택과 초안이 보존되는가?
- 정책 변경 결정과 실제 정책 반영을 구분하는가?
- 좁은 화면과 키보드에서도 선택과 복귀 경로를 사용할 수 있는가?

실제 검토 결과와 한계는 [검토 기록](design/project-detail/review.md)에 남긴다. 저장소 검증은 제품 회귀 검사이며 사용자 이해도 검증을 대신하지 않는다.
