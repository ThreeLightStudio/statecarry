## Stage 4 behavior and regression scope

Goal drafts and save state belong to a work; correction drafts also belong to a candidate. Switching work within the mounted Resume surface preserves edits and the selected candidate. A save submits the version on which its draft was based, and a late response only closes the submitted draft if it has not been edited again. A removed candidate requires an explicit new selection.

A previous brief is retained only when its saved schema, goal/scope and cited evidence remain valid. Same-scope partial/failed reads can retain an already-cited immutable record after checking the connection revision and exact quote. Goal/range changes, incompatible results and changed quotes cannot use this fallback. Original stored records are preserved. The evidence endpoint uses the same access decision as the brief.

Unchanged bounded file-inspection notes remain visible and travel with the handoff; they do not by themselves disable a current action. Changed/unknown workspace state, incomplete records, new unreviewed records, failed checks and explicit producer blocks still require review. Candidate labels reflect the action policy. Preparing and sending a supported continuation both check the stored payload's current evidence and conversation links before dispatch.

Regression tests cover goal/range changes combined with failures, lost and corrupted evidence, stale restore attempts, delayed analysis, repeated explicit refreshes with bounded inspection, work/candidate draft ownership and out-of-order UI responses. Continuation tests use a fake executor to prove that newly inaccessible prepared evidence is not sent. These are automated checks of the implemented boundaries, not observations of real Codex dispatch or human work resumption.

## Stage 5 behavior and validation scope

The default body uses the stored current-state summary, the reason the next action matters, and its completion condition. Evidence attribution is kept separate from a claim of independently verified completion. Raw quotes, project diagnostics, full manual handoff and optional session/coordination tools remain available in collapsed details. Waiting, paused, unclear, completed or blocked work does not acquire an invented executable next step.

Resume browser memory stores selected candidate, goal/action drafts with their original versions, selected reading panels and scroll. It stores no server brief, source quote, busy state or action permission. The Root keeps last-read rows in volatile tab memory for returning from details during an outage; those rows are review-only until a fresh GET confirms the current scope. A successful read that removes work or invalidates a candidate replaces that old view. Changing a browser origin/profile or clearing site storage does not preserve these unsaved edits.

Connection management restores the same connection and work revision through the existing remove/restore commands. Root routing keeps the URL and displayed surface together. Neither reopening a route nor restoring a connection prepares a new model result. The legacy explanation route-entry preparation was removed; its explicit prepare action remains. The Resume change stream surfaces connection loss and reloads saved results on connection recovery, retaining one trailing read when changes arrive during an in-flight GET.

Automated coverage uses the real Root, presentation controller, browser-memory adapter and HTTP routes with synthetic Core records or fake transport/provider boundaries. These tests establish state and command behavior, not that a person understood a real model-generated brief or reached the intended Codex conversation.

## Known gaps

The product remains a development preview. The new production Home/Project flow replaces the competing legacy entry, and scoped database removal is implemented separately from disconnect/restore. Original data, shared source copies and separate diagnostic files/backups are retained as described in the removal preview. The [implementation record](project-ui-implementation.md) distinguishes the checks that passed from real human comprehension and model-quality acceptance still needed. Packaging alone does not establish those outcomes.

Stage 6 must distinguish the viewed build, intended user task, reports and observed behavior. Stage 7 must test whether this product organization is useful before implementing the replacement. Offline cold startup cannot reconstruct a server brief from browser drafts. Cross-device synchronization, installation on another user's Mac, and Electrobun distribution are not established by local route and storage tests.

## Validation still needed

Use multiple goals, including different goals in the same folder and work spanning more than one conversation. Check work changes, edited drafts, refreshes, navigation away and back, restarts, disconnection and restoration. Separate time spent waiting for analysis from the user's understanding and first action.

The original requirement to observe at least three complete real-work returns, including a subsequent return after the action's result arrives, remains unfulfilled and moves to the replacement's acceptance in 7G. A failed stage-6 baseline may proceed to redesign immediately. A copied brief, accepted OS open request or synthetic-provider test alone is not a completed work return. A same-account clean directory check is also distinct from installation by another person or on another device.

The redesign does not automatically expand into task execution, message submission, environment restoration, general project management or multiple new provider integrations. Electrobun supplies application startup, shutdown and installation. Existing auxiliary UI remains only until its use is evaluated: replaced routes/components must be retired in 7G rather than permanently retained as a competing workflow. User records are not deleted by this planning change.
