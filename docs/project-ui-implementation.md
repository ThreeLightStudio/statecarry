## Approved experience

Home helps choose where to spend attention across registered projects. It presents recognizable pending work, results to review and decisions with a reason for each. User-selected focus can lead; recency does not determine priority. All projects remain reachable through the list and search. Selecting a task carries it into the project view.

A project explains its purpose, current goal, last meaningful state, next choice and reason, finish criterion and decision-changing limits. Several tasks can coexist. Ordinary details give prepared explanations; original records require explicit inspection. Waiting, completed and unknown states do not manufacture executable next actions. A project can retain a manually supplied purpose and goal without a conversation. Separate registrations in one folder are not silently merged.

## Implementation and compatibility

The shared contract is `packages/contracts/src/projects.ts`; `GET /api/v1/project-workspace` returns active and disconnected registrations with their current Resume state. Each registration keeps its work and connection identity, title, purpose, explicit focus and acceptance state. Individual paths use `workId`.

Commands use the existing request-ID, expected-revision and payload envelope. Creation uses `POST /api/v1/project-workspace`; its project-specific `settings`, `sources`, `disconnect` and `restore` actions retain scope and ownership. `deletion` previews and commits removal against the current token and revision. Goal edits, corrections, explicit analysis and continuation retain the existing Resume APIs.

The new production Root uses `ProjectController`, `HttpProjectGateway`, `HttpResumeGateway` and `LocalResumeMemory`. The presentation view selects explanatory fields and retains source identifiers for deliberate inspection. Ordinary errors use prepared messages; raw responses are not a display fallback. Existing model instructions were narrowed to require understandable project-specific explanations, but that does not prove actual output quality.

Navigation, detail expansion, manual registration, source settings and reconnection do not initiate model preparation. Source scope, currentness, action validity and late-response rejection remain enforced. Local drafts are not evidence or permission caches and cannot revive removed server tasks. A delayed save from a stopped controller cannot clear a newer controller's input.

Legacy UI modules remain in source for historical regressions, but production Root and old bookmarks no longer enter that competing journey. Existing registrations are reused without a destructive reset. Purpose/title are independent of the current goal. Goal/action drafts use per-work browser storage; unsaved registration and project-settings forms do not claim the same restart persistence.

## Owner follow-up: repeated refreshes

The owner reported excessive repeated state loading after using the replacement. The collection loop checked records every 15 seconds and emitted changes at each thread's read start and at completion, even when the settled result was unchanged. Each notice invalidated the entire workspace. The event-stream handshake also requested the same data through both its connection and change callbacks. The earlier synthetic browser acceptance did not exercise those recurring production observations.

Collection and discovery now compare settled record, scope, link and availability results, excluding observation times and discovery order/cursors. Unchanged checks do not emit data-change notices. Actual changes and failures/recovery emit one notice at the end of the relevant collection or discovery call. Stored reading states and current access checks remain intact. A separate collection-settled event only triggers a read for a client that saw a transient collecting snapshot; ordinary idle clients ignore it.

The project controller coalesces notification bursts within a fixed 150-millisecond window, invalidates changed project permissions immediately and preserves unrelated projects and original inspection. Each stream connection is delivered through one callback. The first connection confirms state once after subscription so a change between the initial GET and stream setup cannot be lost; repeated connected notices do not restart that check. Reconnection rechecks before restoring actions. Background reads keep the explanation, cursor and unfinished input in place. App return checks files and current state without model preparation. The persistent global **Check for changes** action was later removed from the header; the controller operation remains available for situational refreshes. No continuous file watcher or new polling timer was added.
