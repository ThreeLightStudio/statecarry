# Product definition and experience redesign

## Why another stage is required

An initial owner trial after stage 5 reported that the overall flow is still difficult to understand, legacy surfaces remain distracting, and old records cannot be deleted as expected. The owner requested a joint, step-by-step return to problem definition, research, benchmarking, happy-path definition, screen design and potentially a new UI over a headless core. Project-first versus Codex-session-first identity is explicitly unresolved.

Further owner feedback on 2026-09-16 identifies raw records, including unprocessed AI replies, appearing after only one or two levels of detail as a major reading and interpretation burden. This is an explicit design constraint: routine explanations and explanations of evidence must be prepared for the user's decision. Original inspection remains a separately named activity. Merely collapsing the same raw body more deeply does not address this report.

This is user-reported usability evidence. This planning pass has not observed the exact screen, URL, running server build or click sequence from that trial. Record those during stage 6 without dismissing the reported difficulty as a version issue. The source checkout and the application actually visited must be identified separately.

Stages 4 and 5 retain their historical implementation and regression results. Product acceptance is not established. Stage 6 now records the failing baseline and the user's intended outcome; it must not require three successful uses of the rejected layout before redesign may begin. Its original real-work acceptance criteria remain outstanding and must be exercised against the replacement in stage 7G.

Stage 7 below is new. The former installer and submission stages 7A/7B become **8A/8B**. Historical reports keep their original numbers. The ordered delivery path is stage 6 assessment -> joint stage 7 definition/design -> approved implementation and revalidation -> 8A installation -> 8B delivery.

## Product identity: hypotheses to test

Owner clarification received on 2026-09-16: gathering scattered folders made project locations manageable, but returning after external activities still required several conversations to reconstruct purpose, progress and the next choice. The owner now requires project-level understanding and distinguishes unfinished-work returns, completed-work returns and pending delegated results. The common outcome is to understand the immediate next move and check the overall direction. See [the owner-informed 7A definition](problem-definition.md) for the question groups, conditional flows, content requirements and maintenance-cost limits. This grounds the project-oriented requirement without approving a particular schema or screen.

Working hypothesis, not an approved model: **project provides the environment; a work item captures the intended outcome and stopping point; conversations, files and check results supply evidence and possible continuation destinations.** A recent-work entry may be the fastest UI even if projects organize the underlying data. Project-oriented identity does not require an extra project-selection screen on every visit.

| Alternative                          | It may fit when                                                                                         | Failure case to test                                                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Session-first                        | The main job is to find or continue a particular agent conversation.                                    | One outcome spans several sessions, the session is missing, or the desired action has already happened in another session. |
| Project-first                        | The user remembers the repository/environment and wants to recover its current work.                    | Several unrelated goals share a folder, a task spans repositories, or code changes cannot explain the user's intent.       |
| Work/goal-first with project context | The user returns to an outcome and needs decisions/results to survive provider or conversation changes. | Creating and maintaining work items becomes more effort than reopening the original tool; ambiguous tasks are misgrouped.  |

Do not assume one directory equals one project or one project equals one goal. Decide how branch/worktree changes, renamed folders, multiple repositories and multiple sessions affect identity. Model those cases only to the depth needed by the accepted MVP.

Separate **product identity**, **evidence**, and **execution**. A project can reveal files and observed changes but cannot alone prove why a decision was made or whether the user's goal is complete. Conversation text can explain intent but a reported success is not independent verification. A user statement, repository observation and conversation quote should retain their source and time instead of being flattened into one authoritative paragraph.

Codex can remain the first supported adapter without being the permanent identity of the product. Conversely, a session-first product remains a legitimate option if actual tasks support it. If the accepted flow promises provider-independent work, include a meaningful no-Codex/no-session path; never invent missing history or manufacture an action to make an empty screen look complete. If that path adds no value, revisit the promise instead of building a general project manager.

## Initial benchmark evidence

Read 2026-09-15. This is official-document desk research, not a hands-on scorecard or evidence of user preference. Product documentation can change; record the installed version when performing walkthroughs.

| Source                                                                                                                                        | Documented pattern                                                                                                                | Question for StateCarry                                                                                                                                                       |
| --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Zed Agent Panel](https://zed.dev/docs/ai/agent-panel)                                                                                        | Threads can be grouped by project, archived/restored, and used with different agent integrations.                                 | Can users locate the work without recalling a session ID, while still reaching its relevant conversations? Do not assume every external agent supports every history feature. |
| [Conductor workflow](https://www.conductor.build/docs/concepts/workflow), [first workspace](https://www.conductor.build/docs/first-workspace) | A workspace represents a stream of work; the workflow connects repository setup, task execution, review, integration and archive. | What is StateCarry's visible unit of work and natural ending? Its execution environment is not automatically the right scope for a return-assistance product.                 |
| [VS Code Agents window](https://code.visualstudio.com/docs/agents/run/agents-window)                                                          | Active sessions determine associated workspace context and review surfaces.                                                       | Does session-first organization work better for the actual return task? What value would StateCarry add beyond the existing agent interface?                                  |
| [Linear deletion and archive](https://linear.app/docs/delete-archive-issues)                                                                  | Archive and deletion are distinct; deleted items have defined recovery behavior.                                                  | Can users predict where old items go, how to remove them, and what is recoverable? The design criteria also draw on [recognition rather than recall](https://www.nngroup.com/articles/recognition-and-recall/) and [user control and freedom](https://www.nngroup.com/articles/user-control-and-freedom/): recognizable tasks and discoverable exits/undo are useful evaluation lenses, not proof that the prototype is usable.

## Research methods tied to decisions

| Uncertainty                                   | Method and output                                                                                                                               | How the result changes the plan                                                                    |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| What the user came to accomplish              | Reconstruct the most recent real interruption and return. Separate user words, observed actions, and our interpretation.                        | Revise the problem statement and choose the primary task.                                          |
| Whether the product adds value                | Compare ordinary IDE/chat reopening, a short project note, and the proposed StateCarry flow on matched cases. Include setup/maintenance effort. | Keep, narrow, or reject the value proposition. Do not assume all session aggregation is valuable.  |
| Project versus session versus work identity   | Use the same content and goal in small concept sketches; compare first choice, wrong grouping and missing-source cases.                         | Choose identity, grouping and default entry.                                                       |
| First-use and return friction                 | Benchmark only relevant competitor paths; record visible choices, required setup, error/exit paths and outcomes.                                | Borrow useful interaction patterns, not all competitor features.                                   |
| Where understanding fails                     | Walk through real-content wireframes, then run task-based prototype sessions without click-by-click help.                                       | Change labels, content order, screen boundaries or remove features.                                |
| State reliability and data control            | Controlled fixtures and contract tests for stale results, detached sources, late responses, deletion, shared records and restart.               | Refine headless contracts and implementation boundaries.                                           |
| Whether the replacement feels complete in use | Observe real action and a later return; record perceived effort/confidence separately from actual correctness.                                  | Accept or reopen a design decision; do not replace human acceptance with synthetic-agent approval. |

[GOV.UK's moderated-testing guide](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing) recommends realistic tasks with a clear goal without revealing the answer; [NN/g's task-scenario guide](https://www.nngroup.com/articles/task-scenarios-usability-testing/) likewise distinguishes user goals from instructions to click a feature. AI critique and simulated users can find candidate problems, but their output is not a participant observation.

Keep the first research pass bounded: one real primary task, a contrasting goal, one no-session case, and the four benchmark products above. Expand only when an unresolved decision justifies it. Do not spend the remaining MVP time collecting screenshots or producing research reports that do not change a decision.

## Required experience contract, draft v0

The following is a discussion scaffold, not the approved happy path. Decide whether a manually saved stopping point is required or optional before building automatic reconstruction. Ordinary return must not require first-use setup again.

| Moment                 | User needs to understand or do                                                                                 | Experience and state requirement                                                                                                                                                                        |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First entry            | Understand what this app helps finish and choose the relevant environment or work.                             | A concrete example and recognizable starting point. Explain collection scope before reading data; no mandatory session-ID knowledge or full archive import unless research proves it necessary.         |
| Establish the work     | Identify the intended outcome and useful evidence.                                                             | Review suggested sources/goal together, add a short manual goal or stopping point where appropriate, handle missing sources honestly. Show the first useful result without a long configuration detour. |
| Return later           | Recognize the right work among current and old work.                                                           | Stable task identity, clear project context, last meaningful result and unresolved point. Do not rank recency as certainty about priority.                                                              |
| Reorient               | Understand why the work exists, what actually changed and what remains.                                        | One content hierarchy; distinguish observation, report, user decision and suggestion. Optional evidence supports a decision without requiring a reconstruction of all sessions.                         |
| Choose the next step   | Decide whether to continue, correct, pause, finish or remove the work.                                         | A primary action with an understandable consequence. Missing evidence and changed conditions offer a concrete recovery path. No endless re-analysis loop or forced action for completed/waiting work.   |
| Start the action       | Reach the appropriate file, tool or conversation with the required context.                                    | A click or copied message is an intermediate event. Verify the destination and real start. Do not promise generic destinations the implementation does not support.                                     |
| Leave and return again | Keep the new stopping point or meaningful result; prevent already-completed work from returning as a new task. | Capture/adopt the result explicitly or with a visible suggestion. Reentry reads saved state; recovery preserves input. Completion and removal are accessible lifecycle actions.                         |

Required companion paths are part of the flow: wrong task, wrong next action, no project/session, partial source, stale result, server unavailable, cancel/back, disconnected source, archive, deletion and restoration where supported. Specify their minimum outcomes in 7C even if later implementation is sequenced.

## Screen responsibilities, candidates only

No fixed screen count is approved. A panel/dialog may satisfy a responsibility more clearly than a separate route.

| Candidate surface    | Main user question                                         | Minimum content/control                                                                                                     | Content to keep off the primary path                                                                       |
| -------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Work entry/home      | What am I returning to?                                    | Recognizable work with project context, active/paused/completed state, open/add, visible item management.                   | Technical collection IDs, raw thread counts as the only recognition cue, several competing dashboards.     |
| Work detail/resume   | Where did I stop, and what is appropriate now?             | Goal, meaningful latest result/decision, unresolved point, next action or needed decision, edit/finish/pause/remove access. | Repeated summaries, generic status prose, unsupported automatic-session controls.                          |
| Project/source setup | What will this read, and why is it related?                | Recognizable source name, scope/time and proposed relation, manual context option if accepted, disconnect control.          | Transcript previews and the entire collection/checkpoint model before first value.                         |
| Evidence/history     | What supports this statement, or changed this decision?    | Explained findings and limits, source/time, changed-versus-retained information, stable return position.                    | Raw passages or AI replies presented as the explanation; a duplicate summary/continuation workflow.        |
| Original inspection  | Where can I read the exact record or diagnose the failure? | Explicit source/diagnostic action, precise supported destination and return to the pending decision.                        | Automatic entry from a generic detail control or after a failed summary; forced extra explanation screens. |
| Data management      | How do I remove old work and its saved data?               | Distinct hide/archive/disconnect/delete actions, scope preview, recovery policy, result confirmation.                       | A vague Remove label that only hides retained data.                                                        |

Each screen specification must contain its job, entry/exit, content hierarchy with representative real prose, main action, secondary controls, keyboard/focus/back behavior, state matrix and a step-by-step user test. Loading, empty, multiple candidates, stale, failed, disconnected and completed are deliberate states, not layout leftovers.

Owner requirements added on 2026-09-16: explanations at every level must work for someone unfamiliar with internal project terms and prior discussions, and ordinary return must not require interpreting raw data. Keep the immediate reason, expected effect, essential finish criterion and decision-changing uncertainty visible. The revised [content roles](problem-definition.md#explain-without-assuming-knowledge-of-this-projects-internal-terms) replace the earlier layer-2 original-record proposal with explained evidence. Original inspection has its own explicit action; it is not the next explanatory layer. Content roles do not require equally deep routes.

Carry the [return-content contract and case drafts](return-content-contract.md) through the existing gates. In 7C, specify what each step explains and its missing/failed-result behavior. In 7D, write the real default copy, question-specific answers and evidence explanations; document separately what opens original records. In 7E, observe correct decisions with originals closed, plus a separate voluntary verification/return task. In 7F/7G, keep routine presentation contracts from carrying raw display fallbacks and test that error, stale, missing and conflicting states preserve this boundary. These deliverables do not require a new package or another model pipeline.

Create a **keep / simplify / move / remove** inventory for every current major surface. Keep decision-relevant meaning in the routine path; move original records and technical diagnostics to explicitly requested inspection, with source/time and limits still explained near the claim. Obsolete summary pipelines and duplicate continuation screens remain removal candidates. Hiding an obsolete workflow in a new accordion does not count as retiring it. Preserve useful data and tested invariants without preserving every old widget.

## Deletion is a product capability

The present disconnect/restore implementation preserves stored data. The redesign must define actual removal of StateCarry-owned data as well as reversible organization actions. Do not make the user solve local database cleanup to regain a usable workspace.

| Operation                                            | Proposed meaning to review                                                                      | Design obligation                                                                                                                                                                                      |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Hide/archive work                                    | Reduce active-list clutter while retaining resumable history.                                   | Explain whether collection continues, where it can be found and how it returns. This is not deletion.                                                                                                  |
| Disconnect a source or project                       | Stop future collection/analysis under that connection.                                          | State whether previous results remain readable; stop late jobs from republishing hidden or invalidated content.                                                                                        |
| Delete saved StateCarry work/data                    | Remove the selected app-owned item and its associated saved results/edits as defined by scope.  | Preview what is removed and retained; define undo/trash versus immediate permanent removal, with consistent labels. Shared sources cannot be deleted blindly while another work still depends on them. |
| Clear selected imported records/results              | Remove imported copies or generated history within a scope, when required by the selected task. | Invalidate dependent conclusions and references. Distinguish this from deleting the upstream record or regenerating a result.                                                                          |
| Delete original project files or Codex conversations | An upstream destructive action.                                                                 | Outside the default StateCarry data-deletion action. Do not imply it happened; any future support needs its own explicit intent and ownership contract.                                                |

For the chosen deletion scope, cover references, local browser edits, transient view caches, in-flight operations and stored derived results. Specify backup/retention limitations; do not promise secure physical erasure from a generic database delete. Prevent automatic discovery/restart from silently reimporting intentionally removed records. Decide when explicit reconnect may import them again. This planning change performs no deletion of user records.

## Headless rebuild boundary

Begin with the existing `@statecarry/core`, `@statecarry/contracts` and `@statecarry/presentation`. Audit which behavior belongs to the stable domain, which coordinates an application workflow, and which is view-specific. Assess Codex-specific IDs, source schemas and destination URLs separately from React imports. A package can be React-free while still assuming a particular provider or UI workflow.

The accepted design should be exercisable through UI-independent use cases such as listing work, reading a saved return state, recording an intended result, attaching/detaching evidence, explicitly refreshing, reviewing/adopting a change, and deleting within an agreed scope. These are candidate contracts, not required function names. Keep permissions/currentness/attribution, stale-edit handling, query-versus-command separation and late-result rejection out of JSX. Keep scroll, focus and panel presentation out of the domain.

The new UI must not maintain a second, conflicting work model. Reuse Core invariants where they remain correct; amend legacy contracts only where the approved experience requires it. Test with a fake source and a non-React caller. Add a second real provider only when a supported product use case requires it; no general provider framework or separate npm publication is necessary for this rebuild.

For migration, identify actual data ownership, schema changes, shared references and browser state before touching stored data. Build the new happy path as a bounded vertical slice, then replace the default route and remove replaced routes/components after checks. A temporary rollback path is an implementation aid, not a permanent second product navigation.

## Acceptance and the feeling of completion

Treat the owner's strong sense of incompleteness as a usability requirement to investigate, not an aesthetic preference to dismiss or a diagnosis of its cause. Proposed acceptance dimensions are orientation, next-step comprehension, trust in current state, ability to control/remove data, predictable recovery, a visible ending and value on a later return.

Record whether the user can state which work they are in, distinguish a report from a checked result, choose the correct next step, describe what its button will do, and remove an unwanted item with the predicted effect. Observe actions as well as explanations. Separately collect the owner's perceived effort and remaining uncertainty. A confidence rating is not proof that the chosen action was correct.

Measure setup/maintenance effort, time to the first correct decision, time to actual work start, assistance, backtracking and wrong-work actions. Use a baseline and comparable tasks; account for practice/order effects when comparing prototypes. Choose any numeric time/effort target after the baseline with the owner. Do not invent a 30-second threshold or a success percentage from a handful of synthetic examples.

Before accepting 7G, revisit the original stage-6 requirement: at least three complete real-work returns including different goals and multiple conversations, plus a later return after a result arrives. Include the agreed no-session path if that is part of the product promise. Test at least one relevant first-time user's comprehension when feasible and record that limitation if no such observation occurs. Keep real model output, automatic test results, owner observation and independent user observation separate.
